## C. Gaps, contradictions, and decisions the user must make

Ordered by how much of the redesign hinges on them.

### C.1 "The launcher is the sole author" cannot be literally true — the session id is born after launch

D-B says the launcher opens the record with `seq, identity, mode, disposition, budget`. But the launcher never knows the successor's identity: the runtime assigns the session id after the process starts, which is why the `successor-pending-<p>.json` handshake exists (launch:1178-1197) and why the `superseded_by` back-stamp is done by the successor's `register`, "the launcher can't" (docs:717-721). Under `--clear` the id changes inside the *same* process (ADR-0009 §2).

So the record has **two writers by necessity**: the launcher (open: `seq`, `successor`, `mode`, `reason`, `opened_at`, `launched_by` identity of the *dying* session) and `register` (fill: `session_id`, `runtime`, `artifact`, `pid`, `registered_at` of the *new* session). That is still a large reduction (from 7–9 files and ~5 writers), but the plan must say it. Decision: accept two writers with a field-ownership rule (launcher owns lifecycle fields, `register` owns identity fields, nothing else writes), or make `register` the opener and the launcher a "pending" writer — the former is simpler and matches today's handshake.

### C.2 `--clear` (ADR-0009) is both un-exercised and awkward for D-B

VERIFIED: no `/clear` in any local transcript, no `clear` ledger labels. ADR-0009's open item (transcript rotation) is unresolved and decisive: if `/clear` appends, the successor's first `record` reports a false STOP (ADR-0009 "Open item"). Under D-B, `--clear` opens record N+1 whose identity arrives via a `source=clear` SessionStart — the same two-writer shape as C.1 but *without* a process boundary, so `pid`/`artifact` may or may not change. Decision: (a) probe V2 first and keep `--clear` only if rotation is confirmed, or (b) drop `--clear` (the skill's "preferred" path, skill:290-298) and keep spawn as the single relaunch — fewer branches, one fewer state file (`.pending-clear-seed`, which is also the F10 gitignore defect), one fewer hook (`rollover-clear-seed.sh`), and ADR-0009 is superseded. Given zero exercise evidence, (b) is the minimum-code answer; (a) costs one probe.

### C.3 What closes an orphaned record (S6) — the lineage gate's replacement

Today the launcher decides between *reclaim* and *refuse* from three evidence sources gathered since the counter's mtime (launch:504-520) and applies a "resumed-predecessor fingerprint" (:522-565). D-B retires the gate but must answer the same question when it finds the previous record still open. Options, simplest first:

- (c) **Always close as `abandoned`, mint N+1, print the brief.** One rule, no evidence gathering; lineage gaps are visible in the record chain and in the ledger heading (which `check-ledger.py` already validates). Changes the "two doors" contract (work-directory-conventions:119-139: "a session that left no trace gets its number silently reclaimed").
- (b) Reclaim iff the record shows no `last_measured_at` after `opened_at` and `git log --since` is empty (two checks instead of three, both from the record + git).
- (a) Keep today's three-source split.

Recommend (c) or (b); (a) is the cluster D-B exists to remove. Under D-F the ledger-label evidence (today's source (a)) becomes noise anyway (§C.7). This needs the user's call because it changes documented behaviour.

### C.4 What replaces artifact-mtime staleness for a dead lock holder

D-B retires "lock staleness + `--takeover`" as inference. But a session that dies without SessionEnd (kill -9, machine sleep, VS Code crash) leaves `.active-session` held forever unless *something* declares it dead. Today: artifact mtime > `CONTEXT_LOCK_STALE_SECS` (cb:562-577, 733; launch:777-783, 850). Alternatives already on disk: the lock records `pid` + `pid_start` (cb:762-768) and `supervisor_pid`; `holder_process_note` (launch:812-835) already uses pid+start to say "gone or reused". Decision: liveness = `pid` alive with matching `pid_start` (exact, immediate) with mtime as the fallback only where no pid exists (copilot-vscode, cb:700-702). That deletes the 3-hour window and `--takeover`'s main use, keeps `--takeover` as the explicit human override. Note the fleet's child locks (`.agent-locks/`) have *no* pid (subagents are not processes the parent can name) — they keep mtime staleness inside the fleet module (§C.8).

### C.5 "Budget" in the record is two different things

`.session-loop.budget` is a **chain** counter (`used/cap/opened_at/last_seq`, session-loop:104-118, 278-286) that must survive supervisor restarts and *refund* on a logout (:855). A per-session record "closed at the next launch" can carry the chain fields only by copying them forward on every open (`chain_used`, `chain_cap`, `chain_opened_at`), with the supervisor incrementing on the record it opens. Workable, but the plan must not confuse it with the session's *token* budget (`last_measured_tokens`, which D-F writes). Decision: either the record carries both under distinct names, or the chain budget stays its own tiny file (one field, one writer — already the shape D-B wants). Keeping it separate is fewer rules.

### C.6 Runtime scope for supervised chains is narrower than "four first-class runtimes"

VERIFIED: gemini has no turn-end hook and a constant identity (`workspace`); copilot-vscode's `code chat` is detached and `--emit` is refused (launch:732-734). So decision 2's "actually exercise a rollover on each of the four" splits into: attended rollover on all four; **supervised** chain on claude, codex, copilot **CLI** (and opencode if cheap). The plan should state the matrix explicitly and the guide (D-G) must not claim chains for gemini/VS Code. Gemini additionally needs an API key on the origin machine before any live probe (docs:1028-1031).

### C.7 D-F changes what the ledger *means*, and three readers depend on the old meaning

Per-turn (or per-commit) records make `context-ledger.jsonl` a heartbeat, not a work-unit log. Readers today: the lineage gate's "work-unit records since staging" (launch:507-511 — becomes always-true → auto-reclaim never fires; moot if C.3 picks (c)); min-lifetime's "measurement of its own after it started" (session-loop:949-961 — becomes *stronger*, good); statusline pct (unchanged); `work/context-decay` research snapshots (label semantics change). Also cost: a `check` per turn-end on top of the per-tool `check` is cheap for claude (one `jq` on the tail) but the copilot-vscode adapter greps a 4–5 MB file (docs:896). Decision: D-F = turn-end `record` **instead of** the agent's boundary `record`, with `--label` optional; keep `record --label` as an optional annotation, not a rule.

### C.8 D-A vs decision 3: `children` is fleet machinery

Findings D-A lists "dispatch/children/watch" for deletion; decision 3 keeps the dispatch machinery. `children` (cb:1064-1110) is the per-child sweep the fleet's R3 rule depends on (docs:850-854). Reconcile: delete `watch` (F3, layer-3 delivery for hook-less runtimes — note the S9 cost), **move** `children` + `dispatch-*` into the fleet module with its own suite (`test-children-sweep.sh`, `test-dispatch-contract.sh`, `test-dispatch-records.sh` already exist) and its own doc; the daily loop never imports it. Do not fold per-child measurement into the lifecycle record (wrong grain — §B S8).

### C.9 The record must stay gitignored and machine-local

Every file it replaces is gitignored for a stated reason (`.gitignore:29-63`; `.chain-closed`'s rationale at session-loop:112-118: the ignore block is load-bearing for the lineage gate's dirty-evidence leg, and a tracked copy would defeat the stall guard, docs:488-491). A tracked record would (1) dirty the tree every session, (2) make `session_made_progress` true forever, (3) collide across people (S10/E17). Decision: gitignored, and `.gitignore` gains one line and loses seven.

### C.10 Scenario-catalog statements the directions contradict or obsolete

- `scenarios.md` I5 / E16 / ground-truth §D-D describe roles (primary/auxiliary/child/superseded) as a supported, best-tested feature; D-B retires roles. The catalog must be edited in the same change (it is the "canonical external-scenario catalog that committed docs link to", README).
- `scenarios.md` §2 "Session continuity → session numbering, auto-relaunch chain" and I3's "7+1-step procedure" describe the current step count; D-E's slimmer skill changes it.
- `gaps-and-coverage.md` Gap 1 recommends *adding* identity fields and a *non-local heartbeat* for liveness; D-B retires the local liveness heuristic. Not contradictory if C.4 is answered with pid-liveness (stronger locally) and the record keeps `user` — but the plan must say the multi-user heartbeat is still future work.
- `docs/context-budget.md:441-445, 951` (stop hook keyed on `.rollover-complete`) contradicts the code today; D-E must fix regardless.
- CONTEXT.md:286 `--mode interactive` (VERIFIED still present) vs launcher `--loop-mode` (launch:87-92).

### C.11 Smaller holes

- **Hook throttle stamps**: 112 files for 12 sessions (VERIFIED) — D-A's GC is trivial (delete stamps whose session record is gone, inside `register`'s existing purge at cb:802).
- **`rollover-prep.sh` cross-checkout max** (rollover-prep:164-181): retired in the launcher, still printed to the agent as "effective:" — the agent can be told a number the launcher will not use. Delete with D-A.
- **`jq` absence is silent** across all hooks (claude-hook:9, codex-hook:9, gemini-hook:21, copilot-hook:11, stop-hook:20): S9 needs a hard dependency check.

The env comment says a human "writes to the transcript far more often than every 4h"; a human who went to bed does not. Under `mode=interactive` the kill should be off, or D-G's neutral default should be 0.
