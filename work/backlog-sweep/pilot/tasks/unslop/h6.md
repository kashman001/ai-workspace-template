## Proposed Approach: Moving Session Storage To Postgres

In today's rapidly evolving infrastructure landscape, our current session store — a single Redis instance — has become a pivotal bottleneck, highlighting the need for a more robust and holistic solution. This proposal delves into a path forward that is not just incremental, but transformational.

**Current State:** The current state is that sessions live in one Redis node with no replica; a restart in August logged out roughly 18,000 users, underscoring the fragility of this setup.

**Proposal:** The proposal is to store sessions in a new `sessions` table in the existing Postgres cluster, which already serves as the backbone of our data layer and boasts three replicas. Expired rows would be removed by a nightly job, ensuring that the table remains lean.

**Trade-offs:** Trade-offs are, of course, inevitable: session reads are expected to rise from about 1ms to about 4ms at p99, which could potentially be considered acceptable given our 200ms page budget.

**Rollout:** The rollout would be phased — dual-write for two weeks, then switch reads, then remove Redis — fostering confidence at every step.

It is widely believed that this change will significantly enhance reliability, and the future of our session architecture looks bright.
