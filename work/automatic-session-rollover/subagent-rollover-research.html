Research & design note · automatic-session-rollover

Parent-Managed Rollover of Subagent Sessions

Date: 2026-08-06  ·  Status: research/design — no implementation  ·  Source: subagent-rollover-research.md (this page is its review rendition)
Evidence companions: subagent-rollover-stats.md (transcript measurements) · subagent-vendor-survey.md (4-runtime capability survey)

The question. The automatic-session-rollover plan gave the main session a measured, deliberate rollover path (budget hooks → WARN/STOP → pruned handoff → successor launch). Can those learnings extend to subagent (child) sessions, where the parent session — not a human — is the manager? What extra requirements, files, and locking changes does that need? How does it behave at depth, and what resilience is required?

1The problem

LLM quality degrades past ~150K context tokens regardless of advertised window size — the premise of the whole rollover project. Main sessions now have a defense: measurement pushes WARN at 120K and STOP at 150K, and a deliberate, pruned handoff replaces automatic compaction. Child sessions have no such defense, and they are already hitting the danger zone.

Measuring all 30 subagent transcripts in this project's history (peak context = max over each transcript of input + cache_read + cache_creation tokens):

MetricValue
Subagent transcripts measured30
Max peak context141,800 — within 6% of STOP ≥ WARN
Median peak context~66,900
≥ 120K (WARN)3 (10%)
≥ 150K (STOP)0 — but only because tasks happened to be sized right

Top peaks: Task 9 implementer (141.8K), final whole-branch reviewer (133.6K), Task 8 implementer (133.6K), Task 5 implementer (105.6K), vendor-hooks researcher (96.1K). Two readings matter for design:

  • The heavy children are the ones we most need to be smart. Implementers late in their task and whole-branch reviewers enter the "dumb zone" risk band exactly when their judgment matters most.
  • Resumption is a context accretor. The 141.8K peak was an implementer resumed for a review fix round. Every resume stacks a full round of history onto an already-large context — direct evidence that resume ≠ rollover (§2.3).

Claude Code's SDK auto-compacts a subagent that approaches its window, so children don't hard-fail — but auto-compaction deciding what survives is precisely the outcome the rollover project exists to pre-empt (ADR-0003 rationale). The gap is not a protocol — SDD has been field-testing successor dispatch all along — it is a trigger: nobody measures a running child, so nobody rolls it over before quality degrades.

2The model

Everything sufficient for a parent to manage the rollover of a child session reduces to seven elements: roles (who decides), a verb (what "roll over" means for a child), a protocol (how parent and child communicate), files (where state lives), locks (who owns what, and who is alive), state machines (child lifecycle, parent budget modes), and invariants (what must never be violated). The governing rule inherited from the main-session design:

Disk is the authoritative channel; every in-band message is advisory and has a disk counterpart. The system must survive the loss of any in-band leg — a lost nudge or a truncated return degrades to "the parent reads the report file", never to lost state. Liveness is always inferred from artifact freshness, never asserted by an agent; recovery is always re-dispatch from disk, never adoption of a live context.

2.1Roles: the human's job maps onto the parent

The main-session design has a human at the top of every decision. Each human touchpoint maps onto the parent, with one policy change: children never ask the human. Main-session policy is "WARN asks, STOP goes"; child policy is "WARN → parent decides, STOP → parent rolls the child over." Escalation to a human happens only at the top level (L0).

Main-session mechanismChild-session analog
Hook pushes WARN/STOP for the human+agent to act onParent-side check pushes child status into the parent's context — it is the parent's decision loop that must see it
WARN asks the user; declined = write-aheadWARN → parent decides: instruct the child to checkpoint now, or let it finish if near-done
STOP → roll over immediately, no askSTOP → parent stops waiting: instruct the child to flush + return, then successor-dispatch
User pastes the bootstrap prompt / relaunch script runsParent composes the successor child's dispatch prompt from the child's disk handoff
attach-session.sh re-attaches a human terminalNo analog needed — the parent "attaches" by resuming the agent id (continuation, not rollover)
Human notices a dead session and relaunchesOrphan sweep via the lock hierarchy + parent re-dispatch from dispatch records

The signal path is the hard part. All five runtimes have an in-band hook for main sessions, but for a running child only Claude Code fires child-scoped hooks (SubagentStart/SubagentStop, tool hooks with agent_id), and documented context injection lands at the start of the child's conversation — not verified as a mid-flight push. No surveyed runtime reports per-child usage to the parent. Consequence: the reliable, portable signal is the dispatch-time rollover contract written into every long-running child's prompt (report path, checkpoint discipline, a defined ROLLOVER_NEEDED status). Mid-flight hook injection, where it works, is an accelerator — never the load-bearing path.

2.2Two parent positions: root vs intermediate

"Parent" names a role, and two different kinds of node can hold it: the root parent — the main work-item session (depth 0, human-attached, top of the lock hierarchy) — and an intermediate parent — a subagent that itself dispatches children (an L1 orchestrator running L2 workers; depth ≥ 1), which is simultaneously a child of the node above it.

The load-bearing claim: the parent role is position-invariant; the node's own lifecycle is not. Dispatching, probing, findings rounds, drain, and kill rulings work identically at any depth — that is what makes I4 recursive and lets the model compose. Everything that differs comes from the node's own position — who manages it, how it rolls over, and what authority it holds:

DimensionRoot parent (main session)Intermediate parent (subagent)

Design consequence: no separate "parent type" field is needed — position is already derivable from the depth/parent_session_id that R4 puts in every dispatch record. What must be explicit is the table above: statements in this doc about a parent's own rollover, measurement, or authority silently assumed the root until now; for an intermediate parent, substitute this table's right column.

2.3The rollover verb: successor dispatch, not resume

Claude Code can resume a subagent by agentId, and a resumed subagent retains its full conversation history. That makes resume the analog of attach-session.sh — a continuation verb for fix rounds on a child with headroom. It is not a rollover verb: it carries the entire context forward, including everything a deliberate handoff would prune.

Child rollover is therefore always a successor dispatch: (1) the predecessor child flushes state to its report file — ideally on instruction at WARN, at worst whatever its last checkpoint captured; (2) the parent composes a fresh dispatch: the same brief + a "read the report file first — a prior agent attempted this; you own it now" preamble + the open items; (3) the fresh child starts at zero context and demand-loads from disk. This is exactly SDD's round-4 escalation — the superpowers SDD skill has been field-testing child rollover all along, minus the measurement trigger.

2.4Protocol: channels and messages

The governing constraint is asymmetric reachability: a parent can always start a child and always receives its return, but cannot reliably message a running child; a child can always write disk but never interrupt the parent.

ChannelDirectionWhen usableStanding
Dispatch promptP → Cchild startguaranteed, portable
Return messageC → Pchild endguaranteed, size-capped by contract
Resume messageP → Cafter a child stops (claude: by agent_id)runtime-dependent
Hook injectionP → Cchild start (documented); mid-flight (unverified)accelerator only, never load-bearing
Brief fileP → Cany time (child re-reads on instruction)authoritative
Report fileC → Pany timeauthoritative
Dispatch record + child lockparent bookkeepingany timeauthoritative

Parent → child vocabulary:

  • DISPATCH(brief, report, contract, gen) — the opening message. The contract clauses ride inside it: checkpoint at every work-unit boundary, return cap (≤15 lines, detail to the report file), the status vocabulary below, and "if asked to checkpoint, flush and yield — don't push on."
  • CHECKPOINT_REQUEST — the nudge (a resume message): "flush state to your report file now, then return status + open items." Idempotent: a finished child just repeats its final status. This is the only new runtime demand the protocol makes; where resume doesn't exist the parent skips straight to the kill row of the failure matrix.
  • FINDINGS(list) — the existing SDD fix-round continuation. Not a rollover message, but it participates in the budget: every resume stacks history, so the parent charges continuations against the child's remaining headroom.

Child → parent vocabulary:

  • CHECKPOINT — disk-only: append a progress block to the report file. Deliberately doubles as the heartbeat: report-file mtime is the child's liveness signal — no separate keepalive mechanism.
  • YIELD(status) — the capped return. Status extends SDD's contract by exactly one value: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT | ROLLOVER_NEEDED. ROLLOVER_NEEDED means "context spent, task incomplete, report current as of my last checkpoint." A child never emits it from self-assessment (it cannot measure itself) — only in response to a CHECKPOINT_REQUEST or a WARN line its own runtime hook pushed into it. Existing SDD flows are already protocol-conformant.

Two parent actions need no message: probe (measure the child's transcript artifact — throttled, escalation-only, at the parent's own turn boundaries) and kill (no cooperative leg exists or the nudge was ignored: stop the task, mark the child lock abandoned with a ledger ruling, successor-dispatch from the last checkpoint).

Happy path:      P: DISPATCH(gen 1) → C: CHECKPOINT* → C: YIELD(DONE) → P: release child lock
Measured roll:   P: probe ⇒ WARN → P: CHECKPOINT_REQUEST → C: flush, YIELD(ROLLOVER_NEEDED)
                 → P: DISPATCH(gen 2: brief + "read report first" + open items) → … → YIELD(DONE)
Hung child:      P: probe ⇒ STOP / heartbeat stale → P: CHECKPOINT_REQUEST (no yield)
                 → P: kill + ledger ruling → P: DISPATCH(gen 2 from last checkpoint)
Parent drain:    P at WARN: no new DISPATCHes → CHECKPOINT_REQUEST broadcast to live children
                 → collect YIELDs → last child lock clears → parent's own rollover

Generation fencing. The dispatch record carries a generation counter; gen N+1 is dispatched only after gen N's lock is cleared (clean yield or kill), and each report append is labeled with its generation. At most one live writer per report file, and the ledger stays readable as history ("gen 1 attempted X, gen 2 finished it").

2.5Files: what a child rollover needs on disk

Main-session rollover writes project-scoped files. Children need the same shape at task scope — and SDD already defines most of it:

RoleMain session (project scope)Child (task scope)
Forward launcher (replaced)work/<proj>/next-session.mdTask brief — exists in SDD (task-N-brief.md); requirements + pointers, never history
Backward ledger (append-only)work/<proj>/handoff.mdTask report — exists (task-N-report.md, fix reports appended)
Progress map(the ledger)SDD progress.md at plan scope — which children completed
Launch reproduction.rollover-optionsDispatch record new — agent type, model, effort, brief/report paths, status, gen, agent_id
Registry entry.context-budget/sessions/<id>.jsonAgent record new — extended schema: {runtime, session_id, agent_id, parent_session_id, depth, project, artifact}

The dispatch record is the genuinely new file, and it earns its place twice: it lets the parent re-dispatch a crashed or rolled child faithfully (the child analog of option-inheritance), and it makes parent rollover fleet-safe — a successor parent cannot adopt predecessor children (resume is keyed to the parent's session id), but it can reconstruct the orchestration from dispatch records + report files and re-dispatch unfinished subtrees fresh. Without dispatch records, a parent rollover silently loses the fleet. Placement: with the plan/task state that owns them (SDD workspace, or work/<proj>/agents/ for ad-hoc orchestration) — not in .context-budget/, which stays a registry, not a store of prompts.

2.6Locking: from a flat lock to a hierarchy

Minimal extension of today's flat lock: per-child lock files (work/<proj>/.agent-locks/<agent_id>.json) rather than a children[] array — append/remove without rewriting shared state, the same reasoning as session-keyed registry files. The release-order invariant is the mechanical enforcement of "no parent rollover with live children": context-budget.sh release on the parent refuses (or loudly warns) while live child locks reference it — the lock system guarantees the rule rather than trusting skill prose.

2.7State machines

2.8The no-rollover-with-live-children invariant, and drain mode

A parent must not roll over while it has live children. This is correctness, not prudence: successor parents cannot adopt predecessor children (resume is keyed to the parent's session id), so rolling with children in flight strands them — results return to a session that no longer processes them. And the parent's handoff cannot be complete while children are mutating state: "flush — make disk fully current" is unsatisfiable with writers still running.

The mechanism — drain mode (the DRAINING state above): at parent-WARN with children in flight, stop dispatching, let short children complete, nudge long ones with CHECKPOINT_REQUEST, and roll only when the last child lock clears. The successor resumes the fleet by re-dispatch from dispatch records, not adoption.

The refinement — child-aware headroom. Draining is not free: each returning child costs the parent tokens, and the parent must still afford its own rollover ceremony. The honest form is a dispatch guard, not a new threshold:

Don't dispatch a child if current_tokens + (outstanding_children + 1) × expected_return_cost + rollover_reserve > STOP.

Return costs are boundable because the dispatch contract caps them — SDD's "≤15 lines, detail in the report file" rule is precisely this cap. A measured starting value comes from the stats file before implementation.

The escape hatch (resilience, not policy): a hung child must not pin the parent past its own hard limit forever. At parent-STOP with a child ignoring the nudge, the parent kills the child's task, marks its lock abandoned with a ledger ruling, and proceeds. Losing one child's uncheckpointed tail beats losing the parent's entire orchestration to auto-compaction.

2.9Invariants

  • I1At most one valid project-lock holder per work item. (existing lock acquire/steal logic)
  • I2Child lock valid ⇒ its parent's lock valid — transitive validity. (lock validation walks the parent pointer)
  • I3At most one live generation per task; report appends carry their generation. (fencing: gen N+1 only after gen N's lock cleared)
  • I4Parent in ROLLING ⇒ zero live child locks — the drain invariant. (release-order guard in release; skill step ordering)
  • I5Every child terminal state leaves a ledger/report entry — no silent discard, including KILLED. (protocol rule + skill discipline)
  • I6Report files are append-only within and across generations; briefs are replaced only between generations. (write discipline)
  • I7Liveness is inferred only from artifact mtime vs LOCK_STALE, never from any agent's assertion. (all checks route through one age function)
  • I8Anything CHECKPOINTed survives any single failure thereafter. (follows from I5–I7 + disk-authoritative channels; fault-injection confirms)

4.3Depth: second-level children and resilience

With Claude's default depth of 3, an L1 child can itself parent L2 children. The design stays sane only with subsidiarity: each session manages its direct children and nothing deeper. An L1 that parents L2 children applies R1–R7 itself — its own dispatch records, its own drain-before-return; "return" at L1 is its rollover event, and the invariant recurses verbatim. The grandparent never reaches around to grandchildren; it sees only its L1 child's lock, whose validity transitively vouches for (or invalidates) the L2 subtree.

FailureDetectionRecovery
Child crashes/hangsChild artifact mtime stales past LOCK_STALE; parent sees it at its next boundary checkParent re-dispatches from dispatch record + report file; whatever the last checkpoint captured survives
Parent crashes with live childrenParent artifact stales → parent lock invalid → subtree transitively orphanedChildren finish or stall harmlessly (writes are task-scoped files); next session sweeps stale locks, reads dispatch records, re-dispatches unfinished work
L1 rolls over correctly— (drain ran; L2 subtree empty by invariant)Successor L1 rebuilds from records
Whole tree torn down (machine dies)All locks stale on next registerStandard main-session recovery — ledger + report files + git are the record

5The proposal

5.1The delta: requirements beyond main-session rollover

  • R1Parent-side measurement of child artifacts. No runtime reports per-child usage; the parent (or its hook, on the parent's turn boundaries) measures child transcript files directly. Claude-shaped: context-budget.sh check --transcript <project-dir>/<parent-uuid>/subagents/agent-<hash>.jsonl, discovered via the .meta.json siblings. Escalation-only + throttled, or a busy parent gets spammed by N children's WARN lines.
  • R2Dispatch-time rollover contract in every long-running child prompt: report path, checkpoint-at-boundaries discipline, capped return size, defined ROLLOVER_NEEDED status. The disk protocol is load-bearing; hook injection is an accelerator where supported.
  • R3Successor dispatch as the only rollover verb — resume is continuation only, and resumes count against headroom (the 141.8K child was a resumed one).
  • R4Dispatch records persisted by the parent per child (spec + status + agent id), enabling faithful re-dispatch and making parent rollover fleet-safe.
  • R5Lock hierarchy: per-child locks with parent pointers, transitive validity, release-order enforcement (parent release refuses with live children).
  • R6Drain mode + child-aware headroom (§2.8), with the kill-and-ledger escape hatch for hung children.
  • R7Policy relabeling: "WARN asks, STOP goes" becomes, at child level, "WARN → parent decides, STOP → parent rolls the child." Humans are only consulted at L0. ADR-0003's trigger-policy table gains one row; the hybrid principle — ask only where a decision-maker exists in-loop — is unchanged, which is why this is a mapping, not a redesign.
  • R8Recursive application with subsidiarity (§4.3): each level manages only its direct children; R1–R7 apply at every parenting level.

6.2Resilience — fault model and required properties

Faults in scope: crash of any node (parent or child, any depth) at any point; loss/truncation of any in-band message; stale or slow children; concurrent unrelated sessions on the same workspace. Out of scope: disk loss (git + push is the existing answer), clock skew beyond mtime granularity (same exposure as the shipped lock system).

  • P1No lost committed state: anything that reached a CHECKPOINT survives every in-scope fault (I8). Inject: kill -9 the child between and during report appends.
  • P2No orphan writers: post-fault, at most one generation can append to any report (I3). Inject: crash the parent after dispatching gen 2, restart, attempt gen 3.
  • P3Bounded detection: any dead node is detectable within LOCK_STALE by artifact age alone (I7). Inject: manufacture stale mtimes with touch -t, assert sweep verdicts.
  • P4Idempotent recovery: re-dispatch from records + reports is safe to repeat — duplicate successors prevented by fencing; a successor re-reading a complete report re-completes without redoing side effects (side effects live in git-visible files, so "redo" is detectable). Inject: run recovery twice.
  • P5Graceful message loss: drop any single in-band message; the system reaches the same end state via disk, at worst one probe/nudge cycle later. Inject: stub runtime that swallows returns/nudges.

6.3Performance — cost model

The costs that matter are parent-context tokens (the scarce resource this system protects) and wall-clock latency. Parameters marked ★ should be measured from existing registry/ledger data before implementation fixes them.

The full mainline + corner-case scenario suite, enumerated before implementation so it can (a) be held in mind while reviewing the design above and (b) become the acceptance/fault-injection harness. It extends the seed suite S1–S10 (§6.1) and continues its numbering; invariants I1–I8 are in §2.9, fault properties P1–P5 in §6.2. The authoritative, test-derivable source is rollover-scenarios.md in the work directory; this section mirrors it. Class column: M = mainline flow, E = edge/corner case, ★ = measurement (pass = number obtained and bound holds).

7.1The dimension set

The base dimensions were functional mainline, resilience, recoverability, performance. Five more earn first-class status; one candidate folds in:

  • Concurrency & contention — distinct from resilience: nothing fails, things overlap. Drain broadcasts crossing completions, lock steals at the stale boundary, sibling writes, a human attaching mid-drain. Fault injection won't surface these; interleaving will.
  • Vendor heterogeneity & degradation — S10 opens this, but the four-runtime capability asymmetry (§4.2) means degraded modes need their own rows, including mixed fleets, not one representative case.
  • Human-in-the-loop & policy — the seams where automation meets human authority: declined rollovers, manual kills, approval scope across generations, a human taking over a child. Policy edges, not faults; several have no analog in main-session rollover.
  • Observability & auditability — not "does it work" but "can an operator or auditor tell what happened from disk alone." I5 and I7 seed this but don't cover reconstruction or attribution.
  • Evolution & compatibility — records outlive the code that wrote them: schema skew across generations, launch-config (including permission-mode) inheritance, thresholds edited mid-flight.

Folded in, not separate: cost/token-economy is the substance of performance here (the scarce resource is parent-context tokens), so budget-edge scenarios live in the performance group. Resilience vs recoverability, kept distinct: resilience = invariants hold through a fault, automatically; recoverability = the ability to reconstruct and continue from persistent state afterwards, possibly operator-driven. Still out of scope (unchanged from §6.2): disk loss and clock skew beyond mtime granularity.
