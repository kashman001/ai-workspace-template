1. Design overview

Today a Claude Code session rolls over in one of three shapes (docs/context-budget.md:353-366): a fresh process, a supervised --emit (the Stop hook SIGTERMs the session and session-loop.sh runs the staged command), or an attended --clear (the launcher writes the bootstrap prompt plus this process's pid and start time into launch.pending, scripts/launch-next-session.sh:282-285,430-435; the human presses /clear; the SessionStart hook's register matches the pid, binds the new session id to the open launch and prints the prompt into the cleared context, scripts/context-budget.sh:788-795,847-850,865-877).

The --clear path works but is thinly specified: nobody has shown that the cleared session starts working without a typed message; the SessionEnd release hook runs inside a vendor time budget nobody measured; a session can --clear with subagents still running; the turn-end hook kills on staged.by alone; and the supervisor cannot account for a /clear that happened inside a child it is waiting on.

This effort does five small things to the attended Claude path and runs one spike. It does not change how sessions are started on any other runtime and does not build an unattended /clear chain.

  1. Settle the "types nothing" question by probe, then make the skill, the launcher's instruction line and TADR-0009 say what is true (§8).
  2. Pin the hook contracts — SessionStart source=clear output, SessionEnd time budget, turn-end owner check (§3).
  3. Add the drain gate — --clear refuses while a dispatch generation is open (§5), and the skill tells the session what to do with background shells.
  4. Let the interactive supervisor count in-process /clear hops as valid successors by reading one new counter from the record when the child finally exits — no polling, no pty, no event-driven rewrite (§6).
  5. Optional PreCompact auto-block, opt-in (§7).
  6. Spike B: one time-boxed headless run answering six yes/no questions about claude -p + /clear; it changes nothing in the loop (§9).

Requirements

3. Hook contracts

  • S1 — SessionStart source=clear binds the successor (unchanged, now pinned). On a SessionStart payload whose pid walk (scripts/context-budget.sh:683-702) resolves to the pid/pid_start held in launch.pending (scripts/context-budget.sh:788-795), register binds the new session id with action adopted (:847-850), nulls launch.pending, keeps seq (:867-871) and prints the pending prompt once on stdout (:877). A payload whose source is clear but whose pid does not match any pending launch binds nothing and prints nothing. Test: payload fixture with and without a matching pending block; assert record fields and stdout, not prose.
  • S2 — sessionTitle on the clear binding, behind a probe. The hooks page lists sessionTitle among SessionStart outputs (research §2.2, verified against https://code.claude.com/docs/en/hooks); whether it renames an interactive session after /clear is (unverified). Probe A2 (§8) decides. If it applies: for the pending binding on runtime claude only, register prints the JSON form {"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"<prompt>","sessionTitle":"<project> #<seq>"}} instead of the bare prompt, so the title matches what the spawn path sets with --name "<p> #<n>" (scripts/launch-next-session.sh:397). Every other runtime and every non-pending binding keeps plain stdout. If it does not apply: no change; TADR-0009's cosmetic consequence (:130-132) stays and the probe result is recorded there. Test: stdout shape per runtime and binding kind.
  • S3 — SessionEnd stays inside the vendor budget. SessionEnd hooks share a 1.5 s budget; a per-hook timeout raises it (≤ 60 s) and CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS overrides it (research §2.2 and Verification, hooks page + changelog 2.1.74/2.1.268). Our release runs there with no timeout set (.claude/settings.json → SessionEnd). Requirement: (a) measure release wall-clock on this machine ten times under time; (b) set "timeout": 5 on the SessionEnd hook entry regardless, so a slow disk never truncates the owner's ended stamp; (c) document that a truncated release is harmless: register on the new id adopts a same-pid owner whether or not ended was written (:847-850), and a late release from the old id is a no-op for a non-owner (scripts/context-budget.sh:1058) because the compare-and-set keys on session.session_id (:1052-1054). Test: fixture asserting the settings entry carries timeout; the ordering claim is covered by the existing no-op path (assert release with a stale sid returns 1 and writes nothing).
  • S4 — the turn-end hook checks the current owner before any SIGTERM. Today budget_hook_should_exit fires on .staged != null and .staged.by == $sid (scripts/hooks/context-budget-hook-lib.sh:124-134) and budget_hook_exit then kill -TERM $PPID (:141). Requirement: the predicate becomes .staged != null and .staged.by == $sid and .session.session_id == $sid. Why: after a /clear the live process carries a new session id while any surviving background child (changelog 2.1.72, research §2.1) still fires with the old one (scripts/hooks/context-budget-hook.sh:111-113 routes those to a -sidechain key for measurement but the end branch at :81-91 runs before that routing). The research did not reproduce a kill from this path; the check is cheap insurance and also makes the §6 design safe (a --clear under supervision never writes staged, so nothing to kill). Test: record with staged.by == sid but session.session_id != sid → no signal; both equal → signal (existing behaviour).

4. Launch record / session state

Current shape: work/clear-session-loop/session-state.json (schema 1; blocks chain, seq, launch, session, staged; field list at docs/context-budget.md:283-289).

  • S5 — one new counter, chain.clears. Integer, default absent (read as 0). Written only by register on a pending binding (via=pending, scripts/context-budget.sh:788-795) while chain.supervisor is non-null: in the same compare-and-set write that fills session (:865-871), add .chain.clears += 1 and .chain.used += 1. Rationale: the supervisor charges the cap on consume today (scripts/session-loop.sh:338) but is not awake during an in-process hop, so the measurer charges it. Attended (unsupervised) clears touch neither counter — nothing is capping them. No other block changes; launch.pending keeps {pid, pid_start, prompt} (scripts/launch-next-session.sh:430-435); staged is untouched by a clear (test L1g, scripts/tests/test-launch-next-session.sh:339).
  • S6 — launch.mode on a supervised clear is interactive. When --clear runs under a live supervisor (allowed only in interactive mode, S8), the bump writes launch.mode = "interactive" and launch.by = "session"; the successor is in the same process at the same keyboard, so no other mode is possible. Schema number stays 1 — additive fields only; test-doc-consistency.sh pins the record table at docs/context-budget.md:283-289, which gains the clears entry.

5. Drain before --clear

  • S7 — --clear refuses while a dispatch generation is open. Gate name dispatch_open; exit 4 via refuse (scripts/launch-next-session.sh:64), message refused reason=dispatch_open project=<p> open=<task>[,<task>] — checkpoint or close every open generation (scripts/fleet.sh dispatch-list --project <p>), then re-run. Why exit 4 and not 3: the launcher's contract is 0 ok / 3 usage / 4 refused (:26-27); a usage error (die, :63) means the command line is wrong, a refusal means a gate found the workspace not ready and names a remedy — this is the latter, like launcher_unchanged. Detection reuses fleet.sh dispatch-list --project <p> semantics: exit 1 iff any record's last generation has status: "open" (scripts/fleet.sh:288-302). The gate runs for --clear only (a fresh process or --emit orphans children just the same, but that is today's documented behaviour and widening it is out of scope), sits in the --clear block right after the no-pid check (scripts/launch-next-session.sh:282-285) and before worktree_unsynced, and runs under --check and --dry-run too, writing nothing. It is added to the gate table (docs/context-budget.md:331-344) and the pinned reason list (:574).
  • S8 — --clear under a live supervisor. Today refused supervised_stage_only whenever supervised returns live (scripts/launch-next-session.sh:195-197). Requirement: when a supervisor is live and the record's launch.mode is interactive, --clear proceeds (writes launch.pending, S6); in handsoff mode it keeps refusing supervised_stage_only with the remedy text extended: "…or, in an interactive chain, --clear". A plain launch under a supervisor keeps refusing in both modes (test V1).
  • S9 — background shells are the session's job, not a gate's. Nothing in the record tracks run_in_background shells, and they survive /clear (changelog 2.1.72). The skill's step 5 "State snapshot — … running processes" (skills/session-rollover/SKILL.md:157) gains one sentence: before --clear, every background shell is either listed in the launcher with its purpose or killed. No code.

6. Interactive supervisor accepts /clear hops

The supervisor runs the child in the foreground and reads the verdict after it exits (scripts/session-loop.sh:345-392). A /clear inside the child does not exit it, so the research's wording "the press-Enter pause becomes press /clear" (§7 A) cannot be literal: at the pause (:440-445) the child is already gone. What the supervisor can do is accept that the child advanced the number more than once while it waited.

  • S10 — verdict arithmetic uses chain.clears. Let k = chain.clears after minus before the child ran (0 today). The verdict legs change as follows, nothing else:
    • quit legs (:355-372): condition seq_after == seq + k and staged == null; the no_own_measurement check compares session.seq to seq + k.
    • staged leg (:377-392): seq_after == seq + k + 1; launch.predecessor.seq == seq_after - 1 (the last hop's session) instead of == seq; staged.by must still equal launch.predecessor.session_id; lifetime, registered_at ≥ started_iso and mode checks unchanged.
    • any other delta stays staged_invalid leg=seq.
    • the staged verdict line gains clears=<k> so the chain log shows the hop count.
  • S11 — cap and stall. chain.used already includes the hops (S5), so the existing USED -lt MAX_SESSIONS check at the next consume (:334) enforces the cap one child late; document that a child may overshoot the cap by its own in-process hops. The stall guard is off in interactive mode (:430-431), so no change. plan.sh sync/check between children (:393-428, sync at :401) still run at child exit only; the cleared session runs its own plan steps per the skill (docs/context-budget.md:438-441 note).
  • S12 — the pause text. Unchanged; it is correct (the child has exited).

7. Optional PreCompact auto-block

  • S13 — opt-in auto-compaction block. A new PreCompact hook entry in .claude/settings.json with matcher auto, shim scripts/hooks/context-budget-precompact-hook.sh, that exits 2 (blocks, per the hooks page exit-code table — research Verification) only when CONTEXT_BLOCK_AUTOCOMPACT=1 is set in context-budget.env (or the work item's copy) and this session owns a work item (resolve_own_project succeeds). manual is never matched. Default off, because a blocked compaction on a session that ignored STOP is a hard wall at the model's window, not a rollover. Fail-open on every error (no jq, no record, no env). Test: fixture payloads trigger: auto|manual × env on/off × owner/non-owner → exit code only.

Non-goals

Verbatim from research §7 C, plus scope decisions:

  • pty/tmux/expect keystroke injection in session-loop.sh (works empirically, unsupported by every vendor).
  • /clear-based chains on Codex, Copilot, Gemini or the VS Code agents — they keep the fresh-process path; no /clear design for them, and no live verification of their hooks' clear sources.
  • a supervisor rewrite to the event-driven model of research §3.3 for hands-off mode (polling the record, sending /clear).
  • an SDK-hosted headless runner — Spike B only decides whether to propose one.
  • widening the drain gate to --emit or plain launches.
  • changing the bootstrap prompt text (TADR-0003), the record schema number, or the one-owner-per-item rule.
  • D (several sessions per work item) is out of scope; if wanted it is a separate research + spec item (record sessions[], per-lane seq, node claims with CAS — research §6, §7 D).
